# US-AUTO-24: Durable Ledger Workflow Redesign

## Story ID and Title
- Story ID: `US-AUTO-24`
- Title: `Durable Ledger Workflow Redesign`

## Objective
Redesign the story-ledger workflow contract so durable evidence, clean-tree enforcement, review artifact consistency, and terminal finalization semantics can coexist without requiring post-review state drift or post-merge-only evidence.

## Scope
- Define the canonical event model for `story_started`, `review_outcome`, `story_rejected`, and `story_finalized`.
- Define exactly what counts as durable evidence in the Zumbot workflow.
- Resolve when ledger events must be committed relative to run, review, merge, and cleanup.
- Define how review artifacts remain aligned with the exact code under review.
- Define a workflow-safe clean-tree boundary for ledger writes.
- Define operator responsibilities for commits and sequence control.
- Produce a design-only story bundle and registry update; do not implement runtime behavior.

## Non-goals
- Do not modify automation runtime scripts.
- Do not modify tests or production code.
- Do not change review classifications or merge policy beyond the workflow contract needed for durable ledger evidence.
- Do not implement loop detection, budget guards, retry caps, or escalation logic.
- Do not redesign unrelated operator UX or bundle tooling.

## Dependencies
- `US-AUTO-23` delivered the initial evidence-oriented story ledger.
- This story exists specifically because `US-AUTO-23` left an unresolved workflow contradiction around durability, clean-tree boundaries, and review artifact freshness.
- Downstream anti-cycle stories must treat this redesign as their prerequisite contract.

## Current Code Reality
- `story_started` and `review_outcome` evidence can exist before merge review completes.
- `story_finalized` is currently appended only after merge/cleanup, so terminal evidence is not present in the same reviewed and committed feature-branch history as the rest of the run.
- `automation/run_codex_task.sh` currently tolerates ledger dirtiness too broadly, which weakens the clean-tree boundary.
- If a ledger update must be committed after review artifacts are produced, those review artifacts become stale relative to the actual code and ledger state being merged.

## Target Outcome
After this story, Zumbot has a reviewed design contract that states:
- which lifecycle events are canonical
- when each event is written
- when each event must be committed before downstream consumption
- which workflow state owns each event
- how review artifacts stay fresh
- how clean-tree rules treat ledger updates without permitting arbitrary local bypasses
- what operators must commit, when, and why

## Design Recommendation Summary
The recommended workflow is a **feature-branch durable ledger contract**:
- `story_started`, `review_outcome`, and `story_rejected` belong to feature-branch state and must be committed on the feature branch before they are consumed by review or downstream automation.
- `story_finalized` must also become feature-branch-visible durable evidence before merge approval, not a post-merge append on a cleaned-up branch.
- Review artifacts must be generated only after all review-relevant ledger events for that snapshot are already written and committed, so the artifact and reviewed commit range match.
- Clean-tree enforcement may allow only the specific expected ledger write generated by the active workflow step; arbitrary pre-existing ledger dirtiness remains a blocker.

## Architecture Constraints
- Keep the ledger evidence-oriented, not a policy engine.
- Preserve the clean working tree boundary before a run or review step begins.
- Never require a post-review ledger commit that changes the branch snapshot under review.
- Never require a post-merge-only terminal event to satisfy durability for a feature-branch review contract.
- Keep the event vocabulary small and stable.
- Operator actions must remain explicit and auditable in git history.
