# Personal Data & Privacy Notes (MVP)

Документ фиксирует принципы работы с персональными данными (ПДн) в платформе
на уровне архитектуры и логики MVP.

Цель:
- минимизировать хранение ПДн,
- обеспечить обезличивание там, где возможно,
- сохранить удобство работы specialist,
- упростить соответствие требованиям законодательства РФ.

---

## 1. Общие принципы (privacy by design)

1) Храним **минимально необходимый** набор данных.
2) Не храним чувствительные ПДн без явной необходимости.
3) Источник истины по занятости и расписанию — Google Calendar.
4) Telegram используется как канал идентификации, а не как источник ПДн.
5) Платформа не агрегирует данные клиентов между specialist.

---

## 2. Роли и ответственность

### 2.1 Платформа (super_admin)
- оператор сервиса
- хранит технические данные и минимальные ПДн
- не использует данные клиентов в маркетинговых целях

### 2.2 Specialist
- самостоятельный оператор своих клиентов
- несёт ответственность за содержимое своего Google Calendar
- может добавлять приватные заметки к записям

### 2.3 Client
- конечный пользователь
- предоставляет минимальные данные добровольно через Telegram

---

## 3. Какие данные мы храним (MVP)

### 3.1 Specialist
- Telegram ID
- публичное имя (для отображения клиентам)
- timezone
- параметры приёма (расписание, длительность)

Не храним:
- паспортные данные
- адрес
- телефон
- email (если не требуется для OAuth)

---

### 3.2 Client (обезличенно)

Храним:
- `tg_user_id` (технический идентификатор)
- `tg_username` (если есть)
- `display_name` (короткое имя, вводимое пользователем)
- `client_code` (внутренний код, уникальный в рамках specialist)
- `client_timezone`

Не храним:
- номер телефона
- email
- фамилию (если пользователь не ввёл сам)
- историю переписки целиком

Важно:
- `tg_user_id` используется **только** для идентификации в рамках specialist
- один и тот же человек — разные `client` в разных specialist

Примечание:
- `tg_user_id` является единственным стабильным идентификатором пользователя
- `tg_username` может изменяться и хранится только как справочная информация


---

## 4. Что попадает в Google Calendar

### 4.1 Summary (заголовок события)
Формат:
Консультация — {display_name} (#{client_code})


Особенности:
- не используется фамилия
- client_code — технический идентификатор, не являющийся персональными данными вне контекста specialist
- подходит для быстрого ориентирования specialist

---

### 4.2 Description (описание события)

По умолчанию:
- пусто

По инициативе specialist:
- может содержать приватную заметку
- может содержать чувствительные данные (по усмотрению specialist)

Важно:
- такие данные **не обрабатываются платформой**
- ответственность за содержание лежит на specialist
- данные хранятся в Google Calendar, а не в БД платформы

---

## 5. История клиента

### 5.1 В платформе
Платформа хранит:
- список записей (`appointment`)
- даты и статусы
- приватные заметки specialist (опционально)

Это позволяет:
- показывать specialist историю визитов
- показывать client его прошлые/будущие записи

### 5.2 Обезличивание
- история не агрегируется между specialist
- нет глобального профиля клиента
- нет аналитики по поведению конкретного человека

---

## 6. Согласие клиента (MVP)

В MVP согласие реализуется в упрощённом виде:

При первом входе client:
- бот отображает сообщение:
  - что сервис используется для записи на консультации
  - что данные (имя, Telegram ID, записи) используются только для организации приёма
- продолжение использования считается согласием

Юридически:
- формального чекбокса нет
- текст можно доработать позже
- для MVP этого достаточно как “информированное согласие”

---

## 7. Удаление данных

### 7.1 Client
В MVP:
- автоматического удаления нет
- данные хранятся, пока specialist использует сервис

На будущее (не MVP):
- возможность удаления client по запросу
- анонимизация истории (удаление display_name)

---

### 7.2 Specialist
При отключении specialist:
- его данные могут быть помечены как `suspended`
- Google Calendar остаётся под контролем specialist
- данные платформы могут быть архивированы

---

## 8. Логи и обезличивание

В логах (MVP):
- таблица `message_logs` хранит технический контекст диалога и может содержать:
  - `user_handle` (например, @username или имя из Telegram);
  - `content` (текст сообщения/данные callback).
- это полезно для отладки FSM, но потенциально содержит ПДн.

Ограничения и практика:
- доступ к логам ограничен (admin-only);
- для выгрузки используйте `--redact` (см. `docs/logging.md`), чтобы маскировать email/телефоны
  и токеноподобные строки;
- при подготовке аналитики ориентируйтесь на обезличенные идентификаторы:
  `specialist_id`, `client_id`, `appointment_id`, `tg_user_id`.

Дополнительно:
- сообщения об ошибках сохраняются без секретов (см. `60_security_and_compliance/secrets.md`).

---

## 9. Риски и осознанные компромиссы (MVP)

- Google Calendar может содержать ПДн → это зона ответственности specialist
- Telegram username может быть персональными данными → храним минимально
- Нет автоматического удаления данных → допустимо для MVP

---

## 10. Контакт client ↔ specialist (MVP)

Платформа не хранит содержимое переписки между client и specialist.

Сценарий «Написать специалисту» реализован как переход
в личный чат Telegram (ссылка на контакт),
без передачи сообщений через платформу.
