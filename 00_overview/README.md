# Платформа записи клиентов в календарь специалиста (MVP)

## 1. Цель
Платформа предоставляет специалистам (онлайн-консультации) возможность принимать записи клиентов через Telegram-бота, с фиксацией записи в Google Calendar специалиста.

## 2. Роли и термины
### Роли
- `super_admin` — владелец платформы. Полный доступ ко всем данным, настройкам и инфраструктуре.
- `specialist` — клиент платформы (тенант). Владелец своего Telegram-бота, расписания, выбранного Google Calendar и списка клиентов/записей.
- `client` — конечный пользователь, записывающийся к конкретному `specialist`.

### Важный принцип MVP (вариант A с заделом под B)
`client` существует только в рамках одного `specialist`.
Уникальность клиента: `(specialist_id, tg_user_id)`.

## 3. Ключевые продуктовые решения (зафиксировано)
### Telegram
- Для каждого `specialist` используется отдельный Telegram-бот (white-label).
- Все боты обслуживаются одним backend-сервисом (multi-tenant).
- Polling не используется. Только webhooks.
- Webhook URL уникален для каждого бота:
  - `/tg/webhook/{bot_id}/{secret}`
- `specialist` создаёт своего бота самостоятельно через BotFather и передаёт `bot_token` в онбординге.

### Master Bot (онбординг)
- Подключение `specialist` к платформе выполняется только через `master_bot`.
- Онбординг specialist двухэтапный: сначала master-бот (регистрация + привязка personal bot), затем personal bot (подтверждение/редактирование настроек по умолчанию).
- После онбординга все дальнейшие настройки `specialist` выполняет через свой “клиентский” бот.
- В MVP у `specialist` один владелец (owner), определяемый по `owner_tg_user_id`.

### Google Calendar
- `specialist` авторизуется в своём Google аккаунте через OAuth.
- После авторизации:
  - выбирает существующий календарь, или
  - создаётся новый календарь.
- Записи создаются от имени `specialist` в выбранном календаре.
- Видеовстреча (Google Meet) автоматически не создаётся.
- Google является источником истины для timezone календаря:
  - timezone специалиста берётся из Google Calendar timezone.
  - при расхождении с ранее установленным значением специалисту сообщается, что TZ берётся из Google.
  - при работе с календарём timezone проверяется с TTL (MVP-реализация), при изменении обновляется в системе.

### Расписание и слоты
- `specialist` задаёт weekly расписание в платформе:
  - по дням недели,
  - 3 дефолтных интервала на день: утро `09:00–12:00`, день `13:00–17:00`, вечер `17:00–21:00`,
  - повторяется еженедельно.
- “Незанимаемые окна” специалист блокирует обычными событиями в Google Calendar (отдельной логики в платформе нет).
- Шаг слота в MVP: `slot_step_min ∈ {60,30,15,10}`, дефолт 15 минут.
- Длительность консультации — параметр `specialist`, дефолт `60` минут.
- Буфер между сессиями — параметр `session_buffer_min`, дефолт `10` минут.
- Буфер используется только как правило расчёта доступных слотов и **не создаётся** как отдельное событие в Google Calendar.
- Лимит сессий в день — `max_sessions_per_day`, дефолт `4` (не больше 4).
- Склейка стык-в-стык интервалов выполняется только для domain-валидации слота и генерации доступных стартов; UI (когда предлагает выбрать «утро/день/вечер») показывает интервалы в исходном виде (как их задал специалист).
- Если интервал не используется (например, специалист не принимает по утрам), то в БД для него хранится `start=NULL` и `end=NULL`; в UI отображаем `—`.
- Поэтому при domain-проверке допустимости не требуется «закончить сессию до конца первого интервала», если сессия пересекает границу стыка внутри склеенного диапазона.
- Ограничение записи/изменения: только на следующий календарный день и только до 21:00 предыдущего дня по времени specialist (TZ specialist).
- Если текущее время в TZ specialist позже 21:00, следующий день недоступен и показ слотов начинается с послезавтра.
- Показ слотов:
  - по умолчанию — от текущего момента до конца текущей недели,
  - по запросу — следующая неделя целиком,
  - границы недели считаются в timezone клиента.

### Часовые пояса (client)
- Telegram не предоставляет timezone пользователя.
- В MVP:
  - `client_timezone` по умолчанию = `specialist_timezone`.
  - клиент может изменить timezone вручную (выбор в интерфейсе бота).
- Слоты показываются в TZ клиента.
- Если TZ клиента != TZ специалиста, рядом отображается время в TZ специалиста.

### Создание записи и надёжность (MVP без воркеров)
- Подтверждённой запись считается только после успешного создания события в Google Calendar.
- Фоновых воркеров/очередей в MVP нет.
- При создании события в Google выполняется несколько попыток в рамках одного запроса (дефолт: 3 с короткими паузами и таймаутами).
- Если не удалось:
  - запись помечается как failed,
  - клиенту предлагается повторить попытку позже (кнопка retry без повторного ввода данных) или написать специалисту.
- Защита от дублей (двойной клик/повторный callback) обязательна:
  - используется `idempotency_key` и уникальное ограничение в БД.

### Отмена записи (client)
- По умолчанию `client` может отменить запись не позднее чем за 12 часов до начала.
- Если меньше 12 часов — отмена через бота недоступна (MVP: сообщение-заглушка с рекомендацией написать специалисту).

## 4. Источники истины (master data)
- Google Calendar:
  - источник истины для занятости (busy/free) и ручных блокировок/изменений специалиста.
  - источник истины для timezone календаря.
- База данных платформы:
  - источник истины для бизнес-статусов записи (pending/confirmed/failed/canceled),
  - истории клиента в контуре специалиста,
  - правил платформы (cutoff next day + 21:00, окно отмены, weekly availability, длительность сессии,
    минимальный буфер).

В MVP синхронизация при ручных изменениях в Google делается в минимальном режиме:
- занятость учитывается при расчёте слотов всегда,
- для отображения “Мои записи” возможна on-demand проверка события по `gcal_event_id` (минимальный reconcile), без фоновых джобов.

## 5. Компоненты системы (высокоуровнево)
- Backend (единый сервис):
  - Telegram webhook handler (multi-bot routing)
  - Master bot onboarding flow
  - Client booking flow
  - Specialist settings flow (через личного бота)
  - Google OAuth + Calendar API integration
  - DB storage
- Telegram:
  - `master_bot`
  - множество `specialist`-ботов
- Google Calendar API

## 5.1 Домены и публичные URL (production)
- Backend API: `https://api.zumbot.ru` (BASE_URL)
- Сайт/лендинг: `https://zumbot.ru` (PUBLIC_SITE_URL)
- Google OAuth callback: `https://api.zumbot.ru/google/oauth/callback`

## 6. Что сознательно вне MVP / отложено
- Перенос записи (reschedule)
- Уведомления/напоминания (будут спроектированы отдельно)
- Конкурентная запись/блокировки слота (lock)
- Исключения расписания в платформе (отпуска/разовые изменения) — кроме блокировок через Google события
- Несколько администраторов у specialist
- Фоновые воркеры/очереди и периодическая синхронизация
