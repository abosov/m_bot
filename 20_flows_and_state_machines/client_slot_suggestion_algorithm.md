# Алгоритм предложения слотов клиенту (US-03)

## 1. Обзор
В MVP для повышения плотности записи (packing) бот не выводит все доступные окна. Вместо этого он предлагает клиенту выбрать интересующий период дня и выдает 3–4 наиболее подходящих варианта.

## 2. Входные данные
- `specialist_id`
- `target_date` (дата, выбранная клиентом)
- `selected_ranges`: список выбранных периодов (подмножество из {`morning`, `day`, `evening`})
- `client_timezone`
- Параметры специалиста: `session_duration_min`, `session_buffer_min`, `slot_step_min`, `max_sessions_per_day`.

## 3. Определение временных корзин (Bins)
Корзины определяются по **времени специалиста (Specialist TZ)** для группировки и отображения в UI:
- **Утро (`morning`)**: 09:00 — 12:00
- **День (`day`)**: 13:00 — 17:00
- **Вечер (`evening`)**: 17:00 — 21:00

## 4. Этапы расчета

### Этап 1: Формирование списка занятости (Busy Map)
Система собирает все блоки, когда специалист недоступен:
1. **Google Busy**: События из календаря Google.
2. **Confirmed**: Записи в БД со статусом `confirmed`.
3. **Pending (Soft Lock)**: Записи в статусе `pending`. Это критично для предотвращения двойных броней в момент, когда один клиент уже нажал на кнопку, а второй только выбирает.

### Этап 2: Генерация кандидатов
1.  **Склейка интервалов**: Берутся все рабочие интервалы из `weekly_availability` для выбранного дня и склеиваются, если они идут стык-в-стык.
    *   *Пример*: `13:00–17:00` и `17:00–21:00` -> `13:00–21:00`.
    *   *Пример*: `09:00–12:00` и `13:00–17:00` -> остаются двумя отдельными диапазонами.
2.  **Генерация стартов**: Внутри каждого склеенного диапазона генерируются все теоретически возможные старты слотов с шагом `slot_step_min`.
3.  **Фильтрация по правилам**:
    *   **Правило вместимости**: Слот считается валидным, только если вся сессия (`start_time + session_duration_min`) полностью помещается внутри одного из **склеенных** диапазонов.
        *   *Пример*: При диапазоне `09:00–12:00` и сессии 60 минут, последний допустимый старт — `11:00`. Старт в `11:30` невалиден.
        *   *Пример*: При склеенном диапазоне `13:00–21:00` сессия может начаться в `16:30` и закончиться в `17:30`, пересекая границу исходных интервалов.
    *   Исключаются слоты, пересекающиеся с `Busy Map` (с учетом `session_buffer_min`).
    *   Применяются правила `max_sessions_per_day` и `cutoff 21:00`.

### Этап 3: Ранжирование (Ranking Logic)
Для каждой **корзины** (`morning`, `day`, `evening`), запрошенной клиентом, выбираются 3–4 лучших слота из отфильтрованных кандидатов.

1.  **Приоритет 1: Стыковка (Adjacency)**. Слоты, которые минимизируют «дыры» в расписании.
    -   Слот начинается ровно через `buffer` после окончания любого `Busy Map` блока.
    -   Слот заканчивается ровно за `buffer` до начала любого `Busy Map` блока.
2.  **Приоритет 2: Начало диапазона**. Если стыковки невозможны, выбираются слоты, максимально близкие к началу корзины (например, к 09:00).
3.  **Tie-breaker**: При равном весе выбирается более ранний слот.

### Этап 4: Обработка пустых корзин
-   Если в выбранной корзине 0 слотов, бот сообщает: «В это время [Утро] окон нет».
-   Если при этом в других корзинах этого дня есть слоты, бот добавляет: «Но есть варианты днем и вечером» и предлагает по 1-2 лучших варианта оттуда.
-   Если во всем дне 0 слотов — предлагает выбрать другой день.

## 5. Ограничения и допущения
-   **Idempotency**: Нажатие на кнопку слота создает запись `pending`. Если за это время слот заняли в Google, статус сменится на `failed`.
-   **No Pre-hold**: Пока клиент просто видит список кнопок, слоты не резервируются.

## 6. Детальный пошаговый алгоритм `generate_day_slot_starts()` (без кода)

Ниже — целевая логика для функции генерации слотов в рамках одного дня с учетом контекста MVP:
- дефолтные интервалы: `09:00–12:00 / 13:00–17:00 / 17:00–21:00`;
- `slot_step_min ∈ {60, 30, 15, 10}`;
- `session_duration_min = 60`;
- `session_buffer_min = 10`;
- `max_sessions_per_day = 4`;
- `merge_intervals` используется только как domain-операция валидации.

### Шаг 0. Нормализация входа
1. Принять на вход:
   - дату (`target_date`),
   - интервалы доступности дня (`intervals`),
   - длительность сессии, буфер, шаг,
   - текущие подтвержденные/ожидающие сессии дня,
   - внешнюю занятость Google Busy,
   - лимит `max_sessions_per_day`.
2. Привести все времена к timezone специалиста (одна TZ для всей функции).
3. Вычислить:
   - `session_end = start + session_duration_min`,
   - `occupied_end = start + session_duration_min + session_buffer_min` (для конфликтов и packing).

### Шаг 1. Фильтрация `NULL`-интервалов
1. Удалить все интервалы, где отсутствует start или end.
2. Удалить некорректные интервалы (`start >= end`).
3. Отсортировать оставшиеся интервалы по `start`.
4. Если после фильтрации интервалов нет — вернуть пустой список.

### Шаг 2. Merge только для domain-валидации
1. Построить `merged_intervals` (пересекающиеся и стык-в-стык объединяются).
2. Сохранить отдельно:
   - `raw_intervals` (как в настройках, для UI/объяснений),
   - `merged_intervals` (только для проверок в доменной логике).
3. Не менять UI-представление периодов дня из-за merge.

### Шаг 3. Генерация теоретических стартов по шагу
1. Для каждого `raw_interval` генерировать `candidate_start` с шагом `slot_step_min`:
   - старт от `interval.start`,
   - затем `+ slot_step_min`, пока не достигнут `interval.end`.
2. Объединить кандидатов из всех интервалов и убрать дубликаты (например, на стыке `17:00`).
3. Отсортировать кандидатов по возрастанию времени.

### Шаг 4. Доменная проверка каждого кандидата
Для каждого `candidate_start` выполнить проверки в порядке short-circuit:

1. **Вместимость в merged-диапазон**:
   - посчитать `candidate_session_end = candidate_start + session_duration_min`;
   - слот валиден только если `[candidate_start, candidate_session_end]` полностью лежит внутри хотя бы одного интервала из `merged_intervals`.

2. **Учет buffer**:
   - сформировать фактическое занятое окно слота `[candidate_start, candidate_occupied_end)` где
     `candidate_occupied_end = candidate_start + session_duration_min + session_buffer_min`;
   - слот исключается, если это окно пересекается с любым занятым окном из внутренней БД (`confirmed` + релевантные `pending`) или Google Busy.

3. **Лимит `max_sessions_per_day`**:
   - если число уже существующих сессий дня `>= max_sessions_per_day`, вернуть пустой список сразу (ранний выход);
   - иначе слот считается допустимым по лимиту (он потенциально станет очередной, но не нарушает верхний предел).

Все кандидаты, прошедшие 1–3, попадают в `available_candidates`.

### Шаг 5. Фильтрация занятости через Google Busy/Free
1. Запросить Busy/Free по окну дня (минимум `09:00–21:00`, лучше по объединенной рабочей рамке).
2. Нормализовать busy-интервалы в TZ специалиста.
3. Смерджить пересекающиеся busy-интервалы между собой (только для ускорения проверок).
4. Проверять пересечения по полуинтервалам `[start, end)` для исключения пограничных ошибок.

### Шаг 6. Сортировка по приоритету
Для каждого доступного слота вычислить `rank_key`:

1. **Приоритет A: ближе к началу диапазона**
   - найти релевантный диапазон (утро/день/вечер), в который попадает старт;
   - `distance_to_range_start = candidate_start - range_start`;
   - меньшее значение — выше приоритет.

2. **Приоритет B: ближе к существующим сессиям (packing)**
   - посчитать минимальную дистанцию до ближайшей существующей сессии этого дня (или busy-блока):
     - либо по зазору до конца предыдущей,
     - либо по зазору до начала следующей;
   - чем меньше зазор, тем выше приоритет.

3. **Tie-breaker**
   - более раннее время старта выигрывает.

Практически: сортировка по ключу вида
`(distance_to_range_start ASC, distance_to_existing_session ASC, start_time ASC)`.

### Шаг 7. Возврат результата
1. Взять первые `N` слотов из отсортированного списка, где `N` в диапазоне `3..4`:
   - если есть 4+ валидных — вернуть 4;
   - если есть ровно 3 — вернуть 3;
   - если меньше 3 — вернуть все найденные (сигнал для fallback-логики UI).
2. Вернуть слоты в хронологическом порядке отображения.

### Шаг 8. Fallback-поведение (если слотов мало/нет)
1. Если `0` слотов в выбранном диапазоне — сообщить, что окон нет в этом диапазоне.
2. Если в других диапазонах того же дня есть слоты — предложить ближайшие альтернативы.
3. Если слотов нет во всем дне — предложить следующий релевантный день.

## 7. UX-алгоритм выбора в Telegram UI

Целевой пользовательский путь состоит из трех экранов:

1. **Выбор дня недели** (пн–вс или «ближайшие дни» c day-chip).
2. **Выбор предпочтительных диапазонов** (`morning` / `day` / `evening`, multi-select).
3. **Показ 3–4 слотов** согласно выбранным диапазонам и fallback-правилам.

### 7.1. Правила показа слотов

- Если выбран **один** диапазон — выдаем только слоты этой корзины.
- Если выбрано **несколько** диапазонов — показываем слоты в каждой выбранной корзине (с заголовком корзины).
- В UI интервалы дня отображаются **как заданы в настройках** (`raw_intervals`), без merge.
- Доменная валидация вместимости слота выполняется по `merged_intervals` (см. раздел 6).

## 8. Структура `callback_data`

Рекомендуемый компактный формат (для лимита Telegram 64 bytes) — префикс + версия + короткие ключи:

- `bk:v1:day:<dow>:<iso>` — выбор дня.
  - Пример: `bk:v1:day:thu:2026-02-19`
- `bk:v1:rng:t:<code>` — toggle диапазона.
  - `code`: `m` (morning), `d` (day), `e` (evening)
  - Пример: `bk:v1:rng:t:m`
- `bk:v1:rng:apply` — подтверждение диапазонов.
- `bk:v1:slot:<id>` — выбор слота (короткий ID/хеш слота, а не полный timestamp).
- `bk:v1:fb:<type>:<payload>` — fallback-действие (например, `next_day`, `near_range`).

Примечания:
- Полные данные (дата, TZ, список интервалов, ранжирование) хранить в FSM/БД, а не в callback.
- Версионирование (`v1`) обязательно для безопасной миграции формата.

## 9. FSM состояния

Минимальная FSM для клиентского сценария:

1. `BookingFSM.choose_day`
   - Ввод: tap по кнопке дня (`bk:v1:day:*`).
   - Выход: сохраняем `selected_date`, вычисляем `dow`, переходим к диапазонам.

2. `BookingFSM.choose_ranges`
   - Ввод: toggle диапазонов (`bk:v1:rng:t:*`), затем `bk:v1:rng:apply`.
   - Данные FSM:
     - `selected_ranges: set[morning|day|evening]`
     - `selected_date`
     - `client_tz`, `specialist_tz`
   - Guard: `selected_ranges` не пустой (иначе подсказка «Выберите хотя бы один диапазон»).

3. `BookingFSM.choose_slot`
   - Ввод: `bk:v1:slot:*`.
   - На входе в state выполняется расчет + fallback-логика и рендер списка 3–4 слотов.
   - Выход: переход в подтверждение/создание `pending`.

4. `BookingFSM.confirm_slot` (опционально, если есть экран подтверждения)
   - Ввод: confirm/cancel.
   - Успех: создание `pending`, затем доменная проверка актуальности.

## 10. Fallback-сценарии

### 10.1. Пустой один выбранный диапазон
- Сообщение: «В диапазоне *Утро* слотов нет».
- Автопредложение соседнего диапазона:
  - для `morning` → сначала `day`, затем `evening`;
  - для `day` → сначала `morning`, затем `evening` (или ближайший по времени);
  - для `evening` → сначала `day`, затем `morning`.
- Показать 1–2 лучших слота из первого непустого соседнего диапазона.

### 10.2. Выбрано несколько диапазонов, один из них пустой
- Показать слоты из непустых выбранных диапазонов.
- Для пустого диапазона — inline note «нет окон, показаны соседние».

### 10.3. Во всех выбранных диапазонах 0 слотов, но в дне есть слоты
- Предложить CTA: «Показать доступное в этом дне».
- Показать 3–4 лучших слота без фильтра по диапазону (с маркировкой диапазона).

### 10.4. Во всем дне 0 слотов
- Предложить ближайший релевантный день (например, `+1`, `+2`, `+3` дня, где есть окна).
- CTA-кнопки: `Следующий день с окнами`, `Выбрать другой день`.

## 11. Edge cases

1. **Пограничные старты на стыках интервалов** (`17:00` принадлежит двум raw-интервалам):
   - дубликаты удаляются на этапе кандидатов;
   - UI может показывать исходные интервалы раздельно, но слот один.

2. **Сессия пересекает границу raw-интервала**:
   - допустимо только если проходит проверку по `merged_intervals`.

3. **DST / смена часового пояса**:
   - вычисления в TZ специалиста, UI-время клиенту — в `client_timezone`;
   - callback хранит только идентификатор, не локализованную строку времени.

4. **Race condition после показа кнопок**:
   - слот мог стать занятым; на выборе слота повторить domain-check и при конфликте показать «слот уже занят» + регенерацию соседних вариантов.

5. **Меньше 3 валидных слотов**:
   - показываем 1–2, добавляем CTA на соседний диапазон/другой день.

6. **Пустой выбор диапазонов (пользователь снял все toggles)**:
   - не переходить к слотам; показать валидационное сообщение и оставить в `choose_ranges`.

7. **Переполнение callback_data**:
   - запрещено класть full timestamp+tz+meta в callback;
   - использовать короткий slot-id и lookup через FSM/кеш.
