# Booking State Machine (MVP)

Документ описывает жизненный цикл записи (`appointment`) и допустимые
переходы между состояниями в MVP.

Цель:
- иметь единый источник истины по статусам записи,
- упростить реализацию логики,
- избежать противоречивых состояний.

---

## Основные принципы

1. Запись считается подтверждённой **только** после успешного создания
   события в Google Calendar.
2. Google Calendar является источником истины по занятости,  
   но **не** по состоянию записи в платформе.
3. В MVP отсутствуют фоновые воркеры и отложенные ретраи.
4. Все переходы выполняются синхронно в рамках пользовательского запроса.
5. Повторные действия защищены через `idempotency_key`.

---

## Список состояний (`booking_state`)

### `pending`
Запись создана в системе, слот выбран пользователем.
- **Момент создания**: Переход в `pending` происходит в момент нажатия клиентом на кнопку с конкретным временем в Telegram. Простой просмотр списка предложенных слотов НЕ создает `pending` записей.
- **Функция резерва (Soft Lock)**: В MVP это состояние является единственным механизмом блокировки. При расчете доступных слотов для других пользователей, все записи в состоянии `pending` считаются **занятыми** (busy), чтобы предотвратить одновременное бронирование одного окна.
- **Очистка**: Если создание события в Google Calendar завершилось ошибкой, запись переходит в `failed` и слот снова становится доступным для других.

---

### `confirmed`
Событие успешно создано в Google Calendar.

- запись считается активной
- отображается в «Мои записи» у client и specialist
- допускается отмена (при соблюдении cancel window)

---

### `failed`
Не удалось создать событие в Google Calendar
и подтверждено отсутствие события в календаре
(после дополнительной проверки).

- запись не считается подтверждённой
- слот **не считается занятым** в системе
- клиенту предлагается:
  - повторить попытку,
  - или выбрать другой слот,
  - или написать specialist

---

### `canceled_by_client`
Запись отменена клиентом.

- возможно только из `confirmed`
- возможно только если соблюдено cancel window (12 часов)
- событие в Google Calendar удаляется

---

### `canceled_by_specialist`
Запись отменена специалистом.

- возможно только из `confirmed`
- событие в Google Calendar удаляется

---

## Диаграмма состояний (логическая)

       +-----------+
       |           |
       |  pending  |
       |           |
       +-----+-----+
             |
  Google OK   |   Google ERROR
             |
             v
      +------+------+
      |             |
      | confirmed   |
      |             |
      +------+------+
             |
     cancel by client/specialist
             |
             v
 +-----------+-----------+
 |                       |
 |  canceled_by_*        |
 |                       |
 +-----------------------+

pending --(Google error + confirmed absence)--> failed
(после неудачных попыток создания события 
и подтверждённого отсутствия события в Google Calendar)
    
failed --(retry)--> pending

## Допустимые переходы

| From            | To                    | Триггер |
|-----------------|-----------------------|---------|
| —               | pending               | client выбирает конкретный слот (нажатие кнопки) |
| pending         | confirmed             | событие успешно создано в Google |
| pending         | failed                | Google вернул ошибку или таймаут |
| failed          | pending                | client нажал «повторить попытку» |
| confirmed       | canceled_by_client     | client отменил (соблюдено окно 12ч) |
| confirmed       | canceled_by_specialist | specialist отменил в своем боте или Google |


Примечание:
- `failed` устанавливается только после проверки, что событие
  действительно не было создано в Google Calendar
  (см. Google integration, extendedProperties).

---

## Запрещённые переходы

- `failed` → `confirmed` напрямую (только через `pending`)
- `canceled_*` → любое состояние
- `confirmed` → `pending`
- отмена из `pending` или `failed`

---

## Idempotency и повторные действия

### Idempotency key
Для каждой записи используется `idempotency_key`, формируемый из:
- `specialist_id`
- `client_id`
- `start_at_utc`
- `session_duration`

Гарантии:
- повторный клик по слоту не создаёт дубликат записи
- повторный callback Telegram безопасен

### Поведение при повторе
- если `confirmed` → возвращаем подтверждение
- если `pending` → возвращаем сообщение «оформляю запись»
- если `failed` → предлагаем повторить

---

## Источник истины по занятости

- состояние `confirmed` **не означает**, что слот свободен или занят в Google
- занятость всегда проверяется через Google Calendar
- состояние используется для UX и бизнес-логики платформы

---

## Ограничения MVP

- нет состояния `rescheduled`
- нет автоматического восстановления после `failed`
- нет фоновой синхронизации Google Calendar
- нет конкурентной блокировки слотов
