# Booking State Machine (MVP)

Документ описывает жизненный цикл записи (`appointment`) и допустимые
переходы между состояниями в MVP.

Цель:
- иметь единый источник истины по статусам записи,
- упростить реализацию логики,
- избежать противоречивых состояний.

---

## Основные принципы

1. Запись переходит в состояние ожидания подтверждения специалистом только после успешного создания события в Google Calendar.
2. Слот удерживается Google событием уже на этапе ожидания подтверждения специалистом.
3. Google Calendar является источником истины по занятости,
   но **не** по внутреннему `booking_state` в платформе.
4. В MVP отсутствуют фоновые воркеры и отложенные ретраи.
5. Все переходы выполняются синхронно в рамках пользовательского запроса.
6. Повторные действия защищены через `idempotency_key` и проверки текущего состояния.

---

## Список состояний (`booking_state`)

### `pending`
Запись создана в системе, но событие в Google Calendar ещё не создано.

- Момент создания: сразу после выбора конкретного слота клиентом.
- Это техническое промежуточное состояние в рамках запроса.
- При ошибке интеграции переход в `failed`.

---

### `awaiting_specialist_confirmation`
Событие в Google Calendar уже создано, запись ждёт подтверждение специалистом.

- Возникает только после успешного `create event` в Google.
- Слот уже занят, так как Google событие существует.
- Клиент видит статус `Ожидает подтверждение специалистом`.
- Specialist получает действия `Подтвердить` / `Отклонить` в personal bot.

---

### `confirmed`
Запись подтверждена специалистом.

- запись считается активной
- отображается в «Мои записи» у client и specialist
- допускается отмена (при соблюдении cancel window)

---

### `failed`
Не удалось создать событие в Google Calendar
и подтверждено отсутствие события в календаре
(после дополнительной проверки).

- запись не считается подтверждённой
- слот не удерживается, так как Google событие не создано
- клиенту предлагается:
  - повторить попытку,
  - или выбрать другой слот,
  - или написать specialist

---

### `rejected_by_specialist`
Запись отклонена специалистом на этапе подтверждения специалистом.

- возможно только из `awaiting_specialist_confirmation`
- допускает два варианта:
  - с пояснением,
  - без пояснений
- Google событие удаляется (если есть)
- клиент получает уведомление об отклонении

---

### `canceled_by_client`
Запись отменена клиентом.

- возможно только из `confirmed`
- возможно только если соблюдено cancel window (12 часов)
- событие в Google Calendar удаляется

---

### `canceled_by_specialist`
Запись отменена специалистом после подтверждения специалистом.

- возможно только из `confirmed`
- событие в Google Calendar удаляется

---

## Таблица допустимых переходов

| From | To | Триггер |
|---|---|---|
| — | `pending` | client выбирает конкретный слот |
| `pending` | `awaiting_specialist_confirmation` | событие успешно создано в Google |
| `pending` | `failed` | Google вернул ошибку/таймаут и подтверждено отсутствие события |
| `failed` | `pending` | client нажал «Повторить попытку» |
| `awaiting_specialist_confirmation` | `confirmed` | подтверждение специалистом в personal bot |
| `awaiting_specialist_confirmation` | `rejected_by_specialist` | отклонение специалистом (с пояснением или без) |
| `confirmed` | `canceled_by_client` | client отменил (соблюдено окно cancel window) |
| `confirmed` | `canceled_by_specialist` | specialist отменил в personal bot или через Google-синхронизацию |

---

## Запрещённые переходы

- подтверждение специалистом из любого состояния, кроме `awaiting_specialist_confirmation`.
- отклонение специалистом из любого состояния, кроме `awaiting_specialist_confirmation`.
- `failed` → `confirmed` напрямую (только через `pending` и повторное создание события).
- `canceled_*` → любое другое состояние.
- `rejected_by_specialist` → любое другое состояние.
- `confirmed` → `pending`.
- отмена из `pending`, `failed`, `awaiting_specialist_confirmation`, `rejected_by_specialist`.

---

## Инварианты

1. `booking_state = awaiting_specialist_confirmation` или `confirmed` ⇒ `gcal_event_id` должен существовать.
2. `booking_state = failed` ⇒ `gcal_event_id` отсутствует.
3. `booking_state = rejected_by_specialist` ⇒ подтверждение специалистом недоступно.
4. Любое действие specialist `Подтвердить/Отклонить` обязано проверять текущее состояние непосредственно перед update.
5. После перехода в терминальные состояния (`rejected_by_specialist`, `canceled_by_client`, `canceled_by_specialist`) запись не может возвращаться в активный цикл.

---

## Idempotency и повторные действия

### Idempotency key
Для каждой записи используется `idempotency_key`, формируемый из:
- `specialist_id`
- `client_id`
- `start_at_utc`
- `session_duration`

Гарантии:
- повторный клик по слоту не создаёт дубликат записи
- повторный callback Telegram безопасен

### Поведение при повторе
- если `awaiting_specialist_confirmation` → возвращаем сообщение «Запрос отправлен, ожидаем подтверждение специалистом»
- если `confirmed` → возвращаем подтверждение
- если `pending` → возвращаем сообщение «Оформляю запись»
- если `failed` → предлагаем повторить

---

## Источник истины по занятости

- занятость всегда проверяется через Google Calendar
- состояние `awaiting_specialist_confirmation` уже удерживает слот через Google event
- внутренний `booking_state` используется для UX и бизнес-логики платформы

---

## Ограничения MVP

- нет состояния `rescheduled`
- нет автоматического восстановления после `failed`
- нет фоновой синхронизации Google Calendar
- нет SLA на подтверждение специалистом
