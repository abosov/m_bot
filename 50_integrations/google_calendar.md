# Google Calendar Integration (MVP)

Документ описывает интеграцию с Google Calendar:
- OAuth (refresh token / offline access)
- выбор/создание календаря
- получение timezone календаря (истина для specialist_timezone)
- получение занятости (busy/free)
- создание/удаление/обновление событий
- политика ретраев в MVP (без воркеров)

---

## 1. OAuth (подключение Google)

### 1.1 Основная цель
Backend должен иметь возможность:
- читать занятость календаря,
- создавать и удалять события

Для этого требуется OAuth с доступом offline (refresh token),
чтобы backend мог обновлять access token без участия пользователя.

### 1.2 Хранение токенов
- `refresh_token` хранится зашифрованно в БД: `google_oauth.refresh_token_encrypted`
- access token не хранится постоянно (можно кешировать кратковременно в памяти)

Текущее состояние реализации:
- OAuth callback сохраняет refresh token, отмечает статус `connected`
- после успешного подключения отправляет уведомление специалисту в Telegram

### 1.3 Повторное подключение
Если refresh token отозван:
- в MVP пользователь переподключает Google через тот же flow
- backend сообщает рекомендацию и даёт ссылку на OAuth

## 2. Выбор или создание календаря

### 2.1 Выбор календаря
Backend получает список календарей и показывает specialist варианты выбора.
После выбора сохраняет:
- `calendar_id`
- `calendar_title`

Текущее состояние реализации:
- выбор/создание календаря ещё не реализованы.

### 2.2 Создание календаря
Если specialist выбирает “создать календарь”:
- backend создаёт календарь через Google API
- сохраняет `calendar_id`, `calendar_title`

### 2.3 Timezone календаря (истина)
После выбора/создания календаря backend обязан считать timezone календаря и сохранить:
- `specialist_calendar.calendar_timezone`
- `specialist_profile.specialist_timezone` = calendar_timezone

Если timezone изменился относительно предыдущего:
- backend сообщает specialist, что timezone берётся из Google и изменён
- чтобы изменить — нужно поменять timezone в Google

---

## 3. Проверка timezone календаря при работе (TTL)

Поскольку timezone может поменяться вручную в Google:
- backend проверяет timezone календаря с TTL (например 6 часов)
- поле в БД: `specialist_calendar.timezone_checked_at`

Алгоритм:
1) если TTL истёк → запросить timezone календаря
2) если изменился:
   - обновить `calendar_timezone`
   - обновить `specialist_timezone`
   - зафиксировать изменение в логах
   - уведомить specialist при ближайшем взаимодействии (MVP-минимум)

---

## 4. Получение занятости (busy/free)

### 4.1 Источник истины
Google Calendar — источник истины для:
- занятости,
- блокировок и ручных событий специалиста

Платформа не хранит "busy blocks" отдельно.

### 4.2 Какой API использовать
В MVP допустимы два подхода:

A) `freebusy.query`
- на вход получает диапазон времени
- на выход возвращает busy интервалы
- удобно для фильтрации слотов

B) `events.list`
- возвращает события
- можно использовать для reconcile on-demand по `gcal_event_id`

Рекомендация:
- для расчёта слотов использовать `freebusy.query`
- для точечной проверки события (reconcile) использовать `events.get` по `gcal_event_id`

### 4.3 Диапазоны запроса
- запрос busy выполняется на диапазон:
  - текущая неделя (в TZ клиента) → перевод в UTC
  - или следующая неделя → перевод в UTC
- для минимизации нагрузки:
  - ограничивать диапазоны только нужными периодами

## 5. Создание события (create event)

### 5.1 Когда создаём
Событие создаётся только при подтверждении записи клиентом:
- после повторной проверки доступности слота
- после создания `appointment` в состоянии `pending`
- на каждую сессию создаётся ровно **одно** событие
- технический перерыв между сессиями не создаётся как отдельное событие

### 5.2 Параметры события (MVP)
- `summary`:
  - `Консультация — {client.display_name} (#{client.client_code})`
- `description`:
  - пусто (или шаблон)
  - приватная заметка specialist добавляется позже (и может синхронизироваться в description)
- `start`, `end`:
  - задаются корректно с timezone календаря (calendar_timezone)
- Meet link:
  - не создаётся (по решению MVP)

### 5.3 Идемпотентность относительно Google Calendar (MVP+safe)

В MVP основная идемпотентность обеспечивается на стороне БД
(`appointment.idempotency_key`), однако возможен сценарий:

- событие в Google Calendar создано,
- но ответ `events.insert` потерян (timeout / network error).

Чтобы избежать дублей:

1) При создании события backend записывает в Google:
   `extendedProperties.private.appointment_id = {appointment_id}`

2) Если `events.insert` завершился неуспешно или по таймауту:
   - backend выполняет короткую проверку:
     - `events.list` в диапазоне `[start_at_utc - 1h, end_at_utc + 1h]`
     - поиск события с совпадающим `appointment_id`
   - если событие найдено:
     - сохраняем `gcal_event_id`
     - переводим `appointment.booking_state = confirmed`



Дополнительно (зарезервировано):
- можно писать `appointment_id` в описание/extendedProperties,
  чтобы облегчить reconcile

## 6. Ретраи при создании события (MVP)

В MVP нет фоновых воркеров.
Поэтому при `events.insert` делаем несколько попыток в рамках одного запроса:

Рекомендованная политика:
- 3 попытки:
  - попытка 1: сразу
  - попытка 2: через ~1 сек
  - попытка 3: через ~3 сек
- таймаут на каждый запрос: 3–5 секунд

Если все попытки неудачны:
- `appointment.booking_state = failed`
- клиенту: “не удалось подтвердить запись, повторите позже / напишите специалисту”
- кнопка retry (повтор без ввода данных)

## 7. Удаление/отмена события (cancel)

### 7.1 Клиент отменяет запись
Если запись `confirmed` и соблюдено cancel window:
- backend вызывает удаление/отмену события в Google по `gcal_event_id`
- обновляет booking_state в БД

### 7.2 Specialist отменяет запись
Аналогично:
- удаляет событие по `gcal_event_id`
- booking_state = canceled_by_specialist

В MVP удаление выполняется best-effort:
- если Google недоступен:
  - запись в БД всё равно переводится в canceled
  - пользователю показывается сообщение-заглушка
  - (позже можно добавить reconcile/восстановление)

---

## 8. Обновление события (update) — приватная заметка

При добавлении `specialist_private_note`:
- backend обновляет description события в Google

Важно:
- note не показывается клиенту в Telegram
- note может быть видна всем с доступом к календарю (это осознанный риск)

---

## 9. Минимальный reconcile (on-demand, без воркеров)

Проблема:
- specialist может изменить/удалить событие в Google вручную
- у платформы нет фоновой синхронизации в MVP

MVP-решение:
- on-demand reconcile в точках:
  - “Мои записи” (client и specialist) — точечная проверка `events.get` по `gcal_event_id`
  - если событие отсутствует или время изменилось:
    - минимальное сообщение-заглушка
    - предложить уточнить у specialist или переоформить запись

Слоты:
- всегда фильтруются по фактической busy информации из Google,
  поэтому новые брони конфликтов не создают.

---

## 10. Обработка ошибок (MVP)

Типовые случаи:
- `401/403` (token revoked, scopes, access denied)
  - предложить переподключить Google
- `404` (calendar/event not found)
  - заглушка + переподключение/перевыбор календаря
- `5xx` / network
  - применить 3 попытки
  - потом failed

Требования:
- не логировать токены
- логировать коды ошибок и контекст (specialist_id, calendar_id, endpoint)
