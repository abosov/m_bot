# User flow: редактирование профиля специалиста

## Статус
Рабочий flow: форма `/profile/edit` подключена к приватному API и поддерживает сохранение блоков и загрузку медиа.

## Цель
Дать специалисту безопасную точку входа из личного Telegram-бота на web-страницу редактирования профиля и сохранить draft-данные.

## Поток (фактическое поведение)
1. Специалист открывает экран настроек личного бота и нажимает callback-кнопку **«✏️ Редактировать профиль специалиста»**.
   - Если публичная страница уже опубликована и slug валиден, в этом же меню показывается URL-кнопка **«🌐 Открыть публичную страницу»** (`https://zumbot.ru/<slug>`).
2. По callback бот генерирует `web_connect_token` через сервис web-connect.
   - Flow единый для всех уже существующих specialist-owner и не зависит от флагов/дат онбординга (`onboarding_master_completed_at`, `onboarding_personal_completed_at`) или повторной регистрации.
3. Бот отправляет отдельное сообщение в **plain text**: **«Откройте редактор профиля по свежей ссылке»** + URL-кнопку **«Открыть редактор профиля»**.
   - `parse_mode=None`; raw URL не вставляется в текст сообщения.
4. URL имеет вид `/profile/edit#token=<raw_token>` и создаётся в момент нажатия callback.
   - Ссылка одноразовая и действует ограниченное время; старые сообщения не являются долговременной точкой входа.
   - Повторный tap по callback всегда выдаёт новую ссылку без reset/onboarding.
5. Frontend читает token из hash-фрагмента URL (`#token=...`, также поддерживается короткий ключ `#t=...`).
6. Если token присутствует, frontend вызывает `POST /auth/telegram/consume` с JSON `{ "token": "..." }`.
7. Backend валидирует и «поглощает» token, затем выставляет cookie `web_auth_session` (`HttpOnly`, `Secure`, `SameSite=Lax`).
8. При успешном consume frontend удаляет hash из URL (через `history.replaceState`).
9. Если token отсутствует или consume неуспешен, frontend делает fallback-проверку активной сессии через `GET /connect/status`.
10. После успешной авторизации frontend загружает draft: `GET /api/specialist/profile`.
11. Сначала пользователь заполняет и сохраняет блок **«Основное»** (ФИО + специализация). Пока `public_slug` отсутствует, кнопки сохранения остальных блоков и upload-кнопки неактивны с пояснением в UI.
12. При первом успешном сохранении «Основного» backend генерирует `public_slug` (если он был пустой). Frontend после успешного `save-main` синхронизирует состояние через ответ `PUT` и дополнительный `GET /api/specialist/profile`, затем сразу обновляет блок «Публичная страница» и разблокирует остальные секции без перезагрузки страницы.
13. Для каждого save используется `PUT /api/specialist/profile` с полным payload (`merge` на клиенте: `{...state.model, ...patch}`).
14. Блок **«Публичная страница»** показывает статус публикации (`Черновик`/`Опубликовано`), публичную ссылку `https://zumbot.ru/<public_slug>` (если slug задан), кнопку `Копировать` и кнопку `Опубликовать`/`Снять с публикации`.
15. Кнопка публикации вызывает private API:
    - `POST /api/specialist/profile/publish`
    - `POST /api/specialist/profile/unpublish`
    Во время запроса кнопка блокируется; после ответа UI обновляется без reload.
16. Кнопка `Копировать` копирует публичную ссылку через `navigator.clipboard` с fallback на `document.execCommand('copy')`.
17. Медиа-шаги:
    - **Фото профиля**: `POST /api/specialist/profile/photo` (`multipart/form-data`, поле `file`, один файл). После успешной загрузки выполняется обновление списка медиа.
    - **Документы**: `POST /api/specialist/profile/documents` (`multipart/form-data`, поля `file` + `title`). При выборе нескольких файлов frontend отправляет последовательные запросы (по одному на файл). После загрузки выполняется обновление списка медиа.
    - **Список медиа для UI**: `GET /api/specialist/profile/media` (используется на старте страницы и после успешных upload-операций).

## Эндпоинты, реально используемые страницей `/profile/edit`
### Авторизация / сессия
- `POST /auth/telegram/consume`
- `GET /connect/status` (fallback-проверка, если нет валидного token в hash)

### Профиль
- `GET /api/specialist/profile`
- `PUT /api/specialist/profile`

### Публикация
- `POST /api/specialist/profile/publish`
- `POST /api/specialist/profile/unpublish`

### Медиа
- `POST /api/specialist/profile/photo`
- `POST /api/specialist/profile/documents`
- `GET /api/specialist/profile/media`

## UX детали
- У каждого текстового блока своя кнопка **«Сохранить»**.
- Пока `public_slug` отсутствует, доступны только поля блока **«Основное»** и его кнопка **«Сохранить»**; блок **«Цитата»** и остальные save/upload кнопки disabled с пояснением: «Сначала сохраните основную информацию, чтобы создать ссылку профиля.».
- После появления `public_slug` остальные секции разблокируются автоматически без reload.
- До первого сохранения «Основного» профиль считается черновиком без публичной ссылки.
- На успешном сохранении текстовых блоков показывается статус **«Сохранено ✅»** и toast **«Сохранено»** на ~2.5 секунды.
- В блоке «Публичная страница» при отсутствии slug показывается единая подсказка «Ссылка появится после сохранения основной информации.»; кнопка `Копировать` disabled.
- Если профиль не опубликован, показывается подсказка «Пока видите только Вы».
- При запросе соответствующая кнопка блокируется до завершения.
- Текстовые поля trim-ятся на клиенте перед отправкой.
- Ошибки показываются коротким сообщением (без stacktrace).
- Для auth-ошибок используются явные тексты:
  - при `expired_or_used`: «Ссылка устарела или уже была использована. Вернитесь в бот и запросите новую.»
  - при отсутствии token/hash: «Ссылка для входа не найдена. Откройте страницу из бота.»
  - при сетевой/серверной ошибке consume: «Не удалось авторизоваться из-за ошибки сети или сервера…»
- Если consume неуспешен, но `GET /connect/status` возвращает активную cookie-сессию, страница продолжает загрузку профиля без показа auth-ошибки.
- Если backend не может подобрать свободный slug (заняты все suffix `10..30`), UI показывает короткую ошибку `slug_generation_failed`.

## Состав полей на форме
- Основное (порядок в UI): строка ФИО (`first_name`, `middle_name`, `last_name`), затем `specialization`.
- Порядок секций редактора: **Основное → Фото → Цитата → О себе → Образование → Документы → Услуги и цены → Отзывы**.
- Цитата: отдельный блок `hero_quote` с собственной кнопкой «Сохранить», доступен только после появления `public_slug`.
- Контент-блоки: `about`, `education`, `services`, `reviews`
- Медиа: фото (`photo`) и документы (`document`)

## Наблюдаемость
- При успешной генерации ссылки пишется INFO-событие `event=owner_profile_edit_link_generated` с полями `specialist_id`, `tg_user_id`, `path=/profile/edit`.
- Raw token и raw URL не логируются.


## Фото профиля: thumbnail / replace / delete
- В блоке **«Фото»** на `/profile/edit` отображается текущая миниатюра, если фото уже загружено.
- Кнопка с крестиком удаляет только профильное фото (`media_type=photo`) через `DELETE /api/specialist/profile/photo`.
- Загрузка нового фото через `POST /api/specialist/profile/photo` сохраняет инвариант «одно активное фото»: старая запись/файл удаляются, новое фото становится текущим.
- Документы (`media_type=document`) не затрагиваются операциями replace/delete фото.
- После upload/delete UI обновляет список медиа и thumbnail без перезагрузки страницы.

### Smoke checklist
1. Загрузить первое фото → миниатюра появляется.
2. Загрузить второе фото → миниатюра обновляется, остается только одна photo-запись в `/api/specialist/profile/media`.
3. Нажать крестик удаления → миниатюра исчезает, endpoint возвращает `{ok:true}`.
4. Повторить удаление без фото → `{ok:true}`, ошибок нет.
5. Проверить, что документы остаются в списке.
