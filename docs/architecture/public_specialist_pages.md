# Архитектура публичных страниц специалистов

## Цель
Публичная страница специалиста — это мини-лендинг внутри Zumbot по адресу вида `/{slug}` (например, `/TsarevaE_12`).
Страница:
- отображается на основном сайте;
- получает данные о специалисте из backend API;
- использует данные, хранимые в БД;
- является входной точкой в Telegram-бот записи.

## 1) Архитектура страницы специалиста
Архитектура строится как read-only публичный контур на основе существующего backend:

1. **Frontend (website)** принимает запрос на путь `/{slug}`.
2. **Router** проверяет, что путь подходит под правила публичной страницы (валидный slug + не зарезервированный путь).
3. **Frontend Page** запрашивает данные страницы через **Public API** backend.
4. **Public API** читает сущность публичной страницы и связанные данные специалиста из **Database**.
5. Для изображений/файлов Public API возвращает ссылки на **Media storage**.
6. Frontend рендерит мини-лендинг и CTA для перехода в Telegram-бот записи.

Ключевые принципы:
- источник истины для структуры БД — SQL-миграции;
- ORM используется только для работы с данными и не содержит DDL;
- публичная страница изолирована на уровне роутинга, чтобы не ломать существующие страницы сайта.

## 2) Структура URL и маршрутизация
Формат URL:
- `https://zumbot.ru/{slug}`
- пример: `https://zumbot.ru/TsarevaE_12`

Маршрут `/{slug}` обрабатывается как страница специалиста только если одновременно выполняются условия:
1. slug соответствует regex: `^[A-Za-z]+[A-Za-z]_[1-9][0-9]$`
2. slug не входит в список зарезервированных путей.
   Принцип: любые системные/служебные URL (контентные страницы, статика, health-check, robots/sitemap, admin) исключаются из slug-роутинга;
   например: `pricing`, `privacy`, `terms`, `api`, `static`, `assets`, `robots.txt`, `sitemap.xml`, `favicon.ico`, `healthz`, `readyz`, `docs`, `blog`, `specialists`, `admin`.
   Проверка reserved paths выполняется в нормализованном виде (`lower()` + обрезка ведущих/замыкающих `/`), чтобы исключить коллизии из-за регистра и формы URL.

Если условие не выполнено, управление передается существующему роутингу сайта.

## 3) Взаимодействие frontend → backend
Рекомендуемый контракт (пример):
- `GET /api/public/specialists/{slug}`
  - `200 OK` — данные публичной страницы;
  - `404 Not Found` — slug валиден, но страница не найдена/не опубликована;
  - `400 Bad Request` — slug не прошел валидацию формата.

Поток данных:
1. Frontend извлекает `slug` из пути.
2. Проводит базовую проверку формата и reserved list (может быть дублирована backend-валидацией).
3. Вызывает Public API.
4. Backend повторно валидирует slug и выполняет запрос в БД по уникальному полю `slug`.
5. Backend возвращает DTO страницы (контент, данные специалиста, ссылки на медиа, deep-link в Telegram).

## 4) Правила slug
Формат slug:
- `Фамилия транслитом + первая буква имени + "_" + число`
- примеры: `TsarevaE_12`, `IvanovA_21`

Ограничения:
1. regex: `^[A-Za-z]+[A-Za-z]_[1-9][0-9]$`
2. числовой суффикс допускается только в диапазоне `10–30`;
3. slug должен быть уникален в БД;
4. slug должен сравниваться case-sensitive (рекомендуется хранить и искать в канонической форме без автонормализации регистра).

Валидация диапазона `10–30` выполняется отдельно от regex (на уровне backend-логики и/или CHECK constraint в SQL-миграции).

## 5) Данные и хранение
Минимально необходимая модель публичной страницы:
- `slug` (unique, indexed);
- `specialist_id` (ссылка на специалиста);
- публичные поля профиля (имя, описание, специализация, CTA);
- статус публикации (`draft` / `published`);
- ссылки на медиа (avatar, cover, gallery);
- служебные поля (`created_at`, `updated_at`).

Требования к хранению:
- DDL создается только SQL-миграциями;
- ORM-модели отражают уже созданную схему;
- уникальность slug обеспечивается уникальным индексом/констрейнтом в БД.

## 6) Схема взаимодействия
```text
Client Browser
      ↓
Frontend Page (/TsarevaE_12)
      ↓
Public API
      ↓
Database
      ↓
Media storage
```

## 7) Будущие расширения
1. **Каталог специалистов** с фильтрацией по специализации/городу.
2. **Кастомные шаблоны лендинга** (темы, блоки, персональные секции).
3. **A/B-тесты CTA** и аналитика конверсии в Telegram.
4. **Мультиязычность** публичной страницы.
5. **Кэширование public API** для ускорения выдачи и снижения нагрузки.
6. **Версионирование контента** и отложенная публикация.
